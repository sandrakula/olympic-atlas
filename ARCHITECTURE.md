# Архитектура OLYMPIC ATLAS

## Цель

OLYMPIC ATLAS проектируется как база знаний, а не набор независимых страниц. Источником истины станет нормализованная SQLite-база под управлением Prisma. UI и графовая проекция будут читать одну модель, поэтому карточка сущности, статистика и логический запрос не смогут незаметно расходиться.

На текущем этапе база не наполнена спортивными результатами. Схема готова к миграциям, а любые числа в интерфейсе, не относящиеся к структуре приложения, явно обозначены как демонстрационные.

## Основные сущности

### OlympicEdition

Конкретное летнее или зимнее издание игр. Содержит год, сезон, даты, принимающий город и страну. Связано с `Venue` и `Event`. Уникальность определяется парой `year + season`.

### Country

Нормализованная страна или историческое представительство. Хранит код, актуальное и историческое имя, период существования. Связана с атлетами, принимаемыми изданиями, объектами и медальными результатами.

### Athlete

Персона с устойчивым идентификатором, именем и известными датами жизни. Имеет связь с представляемой страной и набором `MedalResult`. Для командных событий позднее потребуется `Team` и таблица состава команды.

### Sport

Верхний уровень спортивной классификации. Содержит набор `Discipline`.

### Discipline

Подраздел вида спорта. Принадлежит одному `Sport` и объединяет конкретные `Event`.

### Event

Соревнование в рамках конкретного `OlympicEdition` и `Discipline`, при необходимости с категорией пола и местом проведения. Связано с результатами.

### MedalResult

Проверяемый итог события: тип медали, место, событие, страна и, если применимо, атлет. Результат не создаётся без источника в процессе импорта; это ограничение будет реализовано в сервисном слое, поскольку SQLite не может выразить его обычным внешним ключом.

### Venue

Спортивный объект, привязанный к изданию, городу и стране. Может быть связан с несколькими событиями.

### KnowledgeSource

Библиографическая запись: заголовок, URL, издатель, даты публикации и обращения, статус надёжности. Через `FactCitation` источник связывается с конкретным полем конкретной сущности, а не только со страницей целиком.

## Карта отношений

```text
Country ──hosts──────> OlympicEdition ──contains──> Event ──has──> MedalResult
   │                         │                        │                │
   ├──represents──> Athlete  └──uses──> Venue         └──part of──> Discipline
   │                     └────────wins/places─────────┘                │
   └────────credited by MedalResult                         belongs to Sport

KnowledgeSource ──supports──> FactCitation ──identifies──> entity + field
```

## Слои приложения

1. **Presentation** — серверные компоненты Next.js для страниц и небольшие клиентские острова для Motion, React Flow и Recharts.
2. **Application** — сервисы вариантов использования: поиск сущностей, получение карточки, обход связей, импорт и верификация. Этот слой будет добавлен вместе с реальными данными.
3. **Domain** — типы знаний, правила валидности, нормализация названий, исторические периоды и словарь отношений.
4. **Data** — Prisma repositories, SQLite, миграции и адаптеры импорта.

Прямой доступ компонентов к Prisma следует ограничить серверными query-функциями. Мутации должны проходить через сервисный слой, чтобы проверять источник, дедупликацию и целостность отношений.

## Логические запросы

Планируется три уровня запросов.

1. **Фильтрация фактов.** Prisma формирует типизированные SQL-запросы: издания по сезону, события по дисциплине, результаты по стране.
2. **Обход отношений.** Сервис строит ориентированный граф из таблиц и выполняет ограниченный BFS/DFS: например, `Athlete → MedalResult → Event → Discipline → Sport`.
3. **Правила вывода.** Детерминированные правила вычисляют производные факты только из источниковых записей. Пример: «страна участвовала в виде спорта на издании», если существует результат или подтверждённое участие связанного атлета в событии этой дисциплины.

Запрос сначала переводится в внутреннее AST:

```ts
type KnowledgeQuery = {
  subject: "athlete" | "country" | "edition" | "sport";
  filters: Array<{ field: string; operator: "eq" | "in" | "between"; value: unknown }>;
  traverse?: Array<{ relation: string; maxDepth: number }>;
  inferenceRules?: string[];
};
```

Компилятор запросов разделит AST на SQL-часть и графовый обход. Каждый ответ должен возвращать не только значение, но и цепочку происхождения: использованные записи, правила и `KnowledgeSource`.

## Поиск

- полнотекстовый поиск по нормализованным именам и альтернативным названиям;
- фасеты по году, сезону, стране, виду спорта и типу сущности;
- переходы по отношениям из карточек;
- подсветка источника каждого факта;
- позднее — SQLite FTS5 для полнотекстового индекса без отдельного поискового сервера.

## Целостность и импорт

- Реальные данные импортируются только из зафиксированного списка источников.
- Сырой импорт сначала попадает в staging-структуры и не виден пользователю.
- Дедупликация использует устойчивые внешние идентификаторы и нормализованные ключи.
- Неоднозначности сохраняются как задачи проверки, а не разрешаются автоматически.
- Медальные результаты должны иметь хотя бы одну активную цитату.
- Исторические страны и переименования моделируются периодами, а не перезаписью прошлого.
