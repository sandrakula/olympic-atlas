# Размещение OLYMPIC ATLAS

Схема рассчитана на один экземпляр Next.js в Railway. Docker собирает приложение и нативный адаптер SQLite на Linux. При запуске контейнер проверяет снимок и миграции на постоянном томе. Рабочая база переносится напрямую в Volume.

## Репозиторий и тариф

Опубликуйте только проверенное дерево исходников в `main`. Исходная SQLite, снимки, .env и вложенные репозитории остаются локальными. В Railway авторизуйтесь в своём аккаунте, выберите «Deploy from GitHub» и разрешите доступ к этому репозиторию. Проверьте ветку `main` в настройках сервиса и оставьте один экземпляр.

## Снимок и первый запуск

1. В корне проекта укажите существующий источник через абсолютный `DATABASE_URL` и запустите `node scripts/production-db.mjs backup <новый-файл-вне-репозитория>`. Скрипт использует SQLite Backup API, проверяет целостность, внешние ключи, FTS5, миграции и контрольные количества. Сохраните SHA-256.
2. В Railway присоедините Volume с путём `/data`. Установите `DATABASE_URL=file:/data/olympic-atlas.db`. На первый перенос можно установить `ATLAS_DB_WAIT_SECONDS=600`. `PORT` задаёт Railway, а для Docker вне Railway действует значение 3000. Healthcheck обращается к `/api/health`.
3. Авторизуйте Railway CLI через `railway login`, привяжите корневой проект командой `railway link` и проверьте сервис, среду и том через `railway status` и `railway volume list`. Через `railway volume files --volume <том> list /` подтвердите, что конечного файла ещё нет.
4. Передайте только проверенный снимок в промежуточный путь. Скачайте загруженный файл обратно и сравните SHA-256. После совпадения переместите его на конечный путь. Команды ниже используют пути относительно корня тома.

```sh
railway volume files --volume <том> upload <локальный-снимок> /olympic-atlas.incoming.db
railway volume files --volume <том> download /olympic-atlas.incoming.db <новый-локальный-файл>
railway volume files --volume <том> rename /olympic-atlas.incoming.db /olympic-atlas.db
```

5. Когда приложение запустится, в **Settings → Networking** сгенерируйте HTTPS-домен и задайте `ATLAS_SITE_URL` его полным адресом. После первого переноса уберите `ATLAS_DB_WAIT_SECONDS`. В логах запуска найдите отчёт SQLite. Ожидаемый текущий срез — 61 издание, 310 спортсменов, 15 участий, 30 результатов, 27 источников, 648 ссылок на факты и 530 документов FTS5. [Управление файлами тома](https://docs.railway.com/cli/volume) · [Подключение тома](https://docs.railway.com/volumes)

## Проверка на публичном адресе

Запустите Playwright с `ATLAS_E2E_BASE_URL`, равным проверяемому HTTPS-адресу. `npm run test:e2e` использует внешний сервис при этой переменной. Набор покрывает интерфейс, пути в графе, все десять правил, FTS5, аналитику и сравнения. Отдельно проверьте доступ без входа, реальные статические ресурсы и попытку загрузки одного внешнего фото. Прочитайте runtime-логи Railway. Запишите дату, URL, версию коммита и размеры данных. Добавьте ссылки в README после проверки. [Healthcheck Railway](https://docs.railway.com/deployments/healthchecks)

## Обновления и сохранность

Перед первым контрольным redeploy создайте резервную копию и зафиксируйте вывод `node scripts/production-db.mjs inspect` через `railway ssh` на выбранном сервисе. Для испытания автодеплоя используйте обычный проверенный push в `main`. После redeploy сопоставьте значения и проверьте FTS5, граф, медали и источники. Том допускает только один обслуживающий экземпляр. На переключении возможен короткий перерыв.

Если появятся новые миграции, сначала проверьте их на копии. Запуск сверяет историю и контрольные суммы. При наличии ожидающих миграций он требует явный список проверенных имён через `ATLAS_APPLY_MIGRATIONS` через запятую. Скрипт сохраняет согласованный снимок перед `prisma migrate deploy`; после обновления база повторно проверяется. Уберите переменную после успешного применения. Seed и массовый импорт не входят в запуск. Railway pre-deploy не используется для работы с томом. [Развёртывания с томом](https://docs.railway.com/volumes)

## Резервные копии и восстановление

- В Railway откройте **Service → Settings → Backups**. При доступности создайте ручную копию перед испытанием redeploy и включите ежедневное расписание. Проверьте лимиты и стоимость дополнительных снимков в выбранном плане.
- Для скачиваемой консистентной копии выполните в `railway ssh` команду `node scripts/production-db.mjs backup /data/atlas-backup-YYYY-MM-DD.db`, каждый раз используя новое имя. Скачайте через `railway volume files --volume <том> download /atlas-backup-YYYY-MM-DD.db <локальный-файл>`, затем проверьте SHA-256 и отчёт `inspect` с абсолютным локальным `DATABASE_URL`.
- Восстановление Railway пересоздаёт состояние тома на момент снимка. Сначала сохраните свежую внешнюю копию, сверьте среду и остановите запись. Проверьте восстановленный сервис и запустите smoke-тесты. При ручном переносе новой базы сначала проверьте её на отдельном стенде. Любую замену рабочей базы выполняйте при остановленном экземпляре с резервной копией и планом возврата. [Резервное копирование Railway](https://docs.railway.com/volumes/backups)
